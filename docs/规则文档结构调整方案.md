# 第二部分：换架构 —— AGENTS.md 索引化（分册 + 路由）

## 8. AGENTS.md 改作索引是否可行

### 8.0 结论

**可行，且本轮实测把它的紧迫性从"优化"升到"止血"。** 但**不能做成"纯目录页"**——必须做成四层：**常驻层 / 触发层 / 案例层 / 强制层**。

### 8.1 决定性实测：常驻前提已经失效

| 项 | 实测 |
|---|---|
| 本会话 system-reminder 实际注入的 AGENTS.md 正文 | **行 1–157 = 15,023 B = 全文 23.0%** |
| 未进入上下文的部分 | **行 158–513 = 50,429 B = 全文 77.0%** |
| 后果 | 规则 2–10、git 与推送策略、会话交互指令**不在任何新会话的上下文里**；它们只在本实例**主动 Read 整份文件**之后才存在 |

> **口径说明（诚实标注）**：注入切点可能随当轮其它内容浮动，**15 KB 不是已确证的固定预算**；但"77% 缺席"是直接观测事实，且与历史记录吻合（此前 AGENTS.md 从 100,670 B 缩减，原因正是"尾部 33% 从未进入任何新会话"）。
> **推论**：第一部分（§3 同层减法）把 65 KB 压到 ≈51 KB，**仍然远超可注入范围**——它解决的是"文件不越界"，**解决不了"规则不在上下文里"**。这正是 §8 存在的理由。

### 8.2 四层模型

| 层 | 载体 | 加载方式 | 定位 |
|---|---|---|---|
| **常驻层** | `AGENTS.md` | **自动注入** | 决策期规则 + 红线 + 路由表 |
| **触发层** | `docs/rules/*.md`（新建） | 按索引路由**主动 Read** | 事件触发型规则全文 |
| **案例层** | `docs/实测档案/`（已有） | 报告与审查时读 | 书名 / 章号 / 数字，**不承载规则句** |
| **强制层** | `scripts/*.py`（已有） | 执行即生效 | **规则的可执行副本**——不依赖是否读到 |

### 8.3 准入判据（三条，决定每一块去哪一层）

1. **触发时机**：每章/每文件动笔都要用 → 常驻；只在特定事件发生 → 触发层。
2. **误犯代价与可逆性**：**静默且不可逆**的不得外置（宁可占字节，不可赌"它读到了"）：
   - 文件命名约定（每次建文件都用）
   - 规则 1–2 原文先行（误犯代价 = 整批作废，Nabokov's Dozen / 100G 两次实证）
   - 8.1–8.3 写作期防缺陷（动笔前必读）
   - git 与推送红线（误犯会把他人改动静默裹挟进 commit）
3. **是否已机械化**：**能写成脚本断言的规则，规则句可以外置**——因为脚本会强制它，这比"移到另一个 md"强一个量级。**只能靠人自觉的流程纪律（如 8.1 证据先行）必须常驻。**

### 8.6 索引区设计（常驻层唯一新增的结构）

放在 `AGENTS.md` 顶部、紧接标题：

```markdown
## 0. 规则路由表（做什么 → 读哪本）

| 何时 | 读 | 关键节 |
|---|---|---|
| 跑完门禁 / 准备 commit | `docs/rules/06-门禁与三档定性.md` | 三档定性 |
| 用户发起五步审查 | `docs/rules/12-审查SOP.md` | 四纪律 |
| 换引语之后 / 写总览之前 | `docs/rules/11-引语修复同步.md` | 四类断言 |
| 归档新 epub | `docs/rules/04-epub归档.md` | 处置表 |
| 写某体裁第一章之前 | `docs/rules/03-格式细则.md` §体裁 | 该体裁 |
| 查脚本命令 | `docs/rules/A-工具链速查.md` | 全 |
| 判断规则是否有效 | `docs/rules/10.4-抽查与前瞻测量.md` | 前瞻测量 |
```

**三条硬要求**：① 「何时」列**不得为空、不得写"需要时"**（触发条件缺失 = 索引失效）；② 「关键节」必须是目标文件中**真实存在的 H2/H3 标题**（校验项 2 会查）；③ 索引只放**路由 + 红线**，**禁放案例与理由**——否则索引自己会重新膨胀回 50 KB。

**红线区**（常驻，全文保留）：文件命名、规则 1–2、8.1–8.3、git 与推送红线、命令块。**红线正文只允许一处**；分册中可以引用，不得复制。

### 8.7 与第一部分（§3 同层减法）的关系

| | 第一部分（同层减法） | 第二部分（分册架构） |
|---|---|---|
| 动作 | 案例迁档案、压体积 | 规则分册、AGENTS 变索引 |
| AGENTS.md 结果 | ≈51.2 KB（余量 21.9%） | **≈25.5 KB（余量 61.2%）** |
| 能否被整份注入 | ❌ 仍不可能 | ✅ 首次可能 |
| 引用可定位 | ✅（§4 P1 锚点化） | ✅（引用天然带文档名） |
| 改动面 | 9 处迁移 + README + 109 处引用 | 再增 7 册新建 + 44 处脚本引用补锚点 |
| 主要风险 | 迁移丢失（低，可逐项核） | **"没读 = 没有"**（结构性，见 §8.8） |

**建议顺序：先第一部分止血（commit A/B 立即做），第二部分单独排期（commit C 之后）。** 三条理由：
1. 第一部分解决"文件越界"这个即刻缺陷，改动小、可回滚；
2. **第二部分会天然吸收第一部分的多数减法项**（#1 工具链表、#2 归档流程、#4 坑位表、#5 三档纪律、#6/#7 测量结论分别落在 7 册里）⇒ 若先做第二部分，第一部分只剩 **#4 / #6 / #7 三项纯去重**仍有独立价值（零风险、立即省 ≈2,462 B）；
3. **两部分的 §号体系必须一次定稿**——否则同一批引用要改两遍。这是不能"先粗后细"的硬理由。

### 8.8 三个失败模式与防护

| # | 失败模式 | 为何危险 | 防护 |
|---|---|---|---|
| 1 | **"没读 = 没有"** | 触发层规则只在实例真去 Read 时生效；漏读一次，规则等于不存在（现在 77% 缺席就是这个形态） | ① 索引每条**必带触发条件**；② 静默不可逆的红线**常驻**（§8.3 判据 2）；③ 关键规则**双写为脚本断言**（强制层） |
| 2 | **索引自身重新膨胀** | 若给每条规则写一句摘要，最终回到 50 KB | ① 索引只放路由 + 红线；② 体积门禁：**> 28,000 B FAIL**、> 26,000 B WARN（E6 由人工纪律升级为脚本） |
| 3 | **N 份文档漂移** | 规范源从 1 份变 8 份，漂移面 ×8（本项目已有 3 处漂移实证） | **双向校验脚本**（§8.9）：索引 → 分册、分册 → 索引 双向对账 |

### 8.9 双向校验脚本设计（新增 `scripts/check_rules_index.py`）

**为什么必须有**：分册化把"单点一致性"变成"8 点一致性"，而本项目既有经验是——**没有脚本断言的清单必然漂移**（两处脚本清单、README 平行副本即实证）。

| # | 检查项 | 档位 |
|---|---|---|
| 1 | 索引路由表「读」列的文件**真实存在** | 阻断型 |
| 2 | 每行「关键节」在目标文件中**可 grep 到**（匹配 `^#{2,3} ` 标题） | 阻断型 |
| 3 | **反向孤儿检测**：`docs/rules/*.md` 的每个 H2 **必须被索引登记** | 提示型 |
| 4 | `AGENTS.md` 体积：> 28,000 B FAIL；> 26,000 B WARN | 阻断型 / 提示型 |
| 5 | 分册内**禁裸写「第 N 条」**（必须 `§N` 或 `文档名 §N`） | 阻断型 |
| 6 | 常驻红线句在分册中被复制 → WARN（提示"两处需同步"） | 提示型 |
| 7 | 每册首行须带触发注释 `<!-- 触发：… -->`，缺失则 WARN | 提示型 |

**接入方式**：仅当 `AGENTS.md` 或 `docs/rules/` 有改动时才参与提交门禁（不给精读批次增加无关噪声）；输出沿用本项目三档文化（阻断 / 提示 / 假红），**假红一律先修脚本**。

### 8.10 尚未验证的三件事（诚实标注，不写成结论）

1. **注入预算是否固定**：只观测到一次 ≈15 KB 的切点。**建议加"注入探针"**——在 AGENTS.md 尾部放一行哨兵，每轮会话开头让实例自报"AGENTS.md 注入止于第几行 / 是否看到哨兵"，累计几轮后再定为硬预算。
2. **`read_when` frontmatter 是否对任意文档生效**：观察到身份文件（`SOUL.md` / `USER.md`）带 `read_when:` 字段，但**未知 harness 是否对 `docs/` 下普通文档也做条件注入**。若生效，触发层可升级为"按 `read_when` 自动加载"，**§8.8 风险 1 基本消解**——这是本架构收益最大、也最需先验证的一点。
3. **实例是否真会按路由去 Read**：只能靠实践统计（可记"分册被 Read 次数 ÷ 该事件实际发生次数"，作为索引有效性的指标）。

**建议的最小验证动作**（不动任何现有规则文件）：新建 `docs/rules/_probe.md`（含 `read_when:` 字段 + 一句哨兵），下一轮会话观察它是否被自动注入 ⇒ **一次实验同时回答问题 1 与 2**，再决定是否铺开。
