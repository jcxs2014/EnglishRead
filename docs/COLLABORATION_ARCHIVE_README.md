约定：

- 排序规则全局统一 **newest first**（主板与所有归档一致），时间戳 UTC `YYYY-MM-DD HH:MM UTC`。
- 归档文件为**只读历史**，不再修改（勘误除外）；新消息一律写主板顶部。
- 归档文件头部用精简格式（标题 + 归档说明 + 归档索引），**不复制**主文件的说明区。
- 主板头部 `> **📁 历史归档**：` 索引行随归档动作同步更新，四个文件互相可跳转。**位置固定在 `> **排序规则**` 行上方**——离消息插入点更远，防止实例写新消息时覆盖说明区；新消息一律插到消息区 `---` 之后、第一条消息之前，不得改动说明区两行引用块。

## 归档时机

主板超过 **~100 条消息或 ~100KB** 时归档（由用户发起，实例可提醒但不自动执行）。

## 归档操作规范（硬规则）

1. **先修序，再切割**。切割前先按消息**首次时间戳**（标题行 `[YYYY-MM-DD HH:MM]` 的第一段时间，忽略"→ 更新 HH:MM"）对全部消息做稳定降序重排（同时间戳保持原相对顺序）。
   > **实证教训（2026-09-18）**：ARCHIVE_260916.md 版归档基于乱序主文件按物理位置切割，把一条 `09-16 06:50` 的消息误归进旧档（它被插在 09-15 区域），整版被回退（780b9aa6）。当时主文件 179 条中有 28 处乱序，尾部 7 条跨 09-05~09-13 的消息堆在 09-04 区域之后。
2. **修序验证三关**（全过才动切割）：
   - 乱序点 = 0（相邻消息时间戳单调不增）；
   - 消息块内容多重集合与修前一致（只许挪位置，不许动内容）；
   - 消息总条数守恒。
3. **按日期段切割**，归档文件命名 `COLLABORATION_ARCHIVE_<段截止日YYMMDD>.md`；单文件控制在 **~150KB** 以内，超了就多拆几段（段边界优先放在消息量低的日子）。
4. **切割后验证**：主板 + 各归档条数 = 修序版总数；消息块多重集合并集与修序版一致；无重复块；每个归档的日期全部落在自己声明的范围内。
5. 主板保留段 = 最近日期段（含被修复归位的新消息）；更新主板头部索引行。
6. **多实例并行保护**：写入前重读最新版主板（防覆写丢消息）；`git add` 只加明确路径（主板 + 新归档 + 被删旧归档），禁止 `git add -A`。
7. 归档动作在 commit message 中写明：各文件范围、条数、守恒验证结论；若删除旧归档，说明删除原因（git 显示的 rename 是内容子集相似所致，message 里要写清实际变更）。
