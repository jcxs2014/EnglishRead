## 1. 目的

1. 一本书 → 逐章精读 md（+ 总览三篇）；一篇文章 → 一篇 md。格式随本书既有形态，不套全局模板。
2. 精读必须**忠实于原文**。忠实不是一句话，是四个可分别验收的东西（见 §2）。
3. 成本要撑得住长篇（30–100 章），且写完当场能自查，不依赖另一个会话。

## 2. 质量判据：忠实四问

| 类 | 问 | 现在谁在管 |
|---|---|---|
| 逐字 | 引语在原文里一字不差吗 | 11–lane 数（以 `gate.sh` 现场为准）（已过度覆盖） |
| 对应 | 分析讲的是这一段吗 | `chapter.sh` 弱覆盖 + R4 人判 |
| 可回溯 | 事实/数字断言回得到原文吗 | **零覆盖** → R1 素读 + R3 对账 |
| 不漏 | 关键内容没被略过吗 | **零覆盖** → R1 素读（先读 text 后开 md） |

## 3. 两步流程

- **创建**：`docs/rules/创建卡.md`（三句话 / 开工命令 / 生产五步 / 门禁四档 / 三条硬线 / 三条禁令）。

  - 独立性来源＝**把读的顺序倒过来**：R1 先只读 `text/chNN.txt` 写素读，写完才开 md。
  - 审查包落 `.memory/raw-gates/<slug>/chNN/`：`1-suread.json`、`2-machine.json`、`3-diff.md`、`4-verdict.md`、`run.sh`。
  - 第三方复核三步：跑 `run.sh` → 比 `2-machine.json` 哈希 → 抽 3 行 `4-verdict.md` 回原文。

## 步骤 5 结论：raw-gates 现在**没有**可删的余地（2026-10-20 实测）

原计划写「保留最近 30 天 + 每本书最后一次，其余 `git rm --cached`」。实测推翻了三点：

1. **「30 天」永远剪不到**：全库最早的运行是 2026-10-11（距今 9 天）——这是活跃库，
   按天数剪枝等于没有策略。
2. **「每本书最后一次」只能删 132 / 2,315 个文件（5.7%）**：同一次运行本身就有几十个文件
   （逐章 + 全量门禁 + 各 lane 分件），真正的体量不在「历史运行太多」。
3. **原件被引用钉死**：`docs/`、`.memory/daily/`、`COLLABORATION.md` 里有 **193 处**
   按「目录/文件名」引用具体某一次运行的原件。删掉即断链，而引用检测只能认出
   **9 个**可保护的（slug, 文件名）对——检测不完美，删了会静默断链。

⇒ **政策（已生效）**：
- 证据**保持入库**，不因体积删；`.memory/raw-gates/` 仍是唯一允许的过程落盘点。
- 每本书**只保留最近一次运行**是目标态，由 `scripts/prune_raw_gates.py` 执行（默认演练、
  自动跳过被引用文件、最新一次不完整的目录整目录跳过）。
- **每季度**跑一次 `python3 scripts/prune_raw_gates.py` 看增长；确认无引用断链风险再 `--apply`。
- 真要让仓库变小，正确方向不是删证据，而是**证据文件本身瘦身**（gate 输出只留汇总行，
  逐条明细进 git 历史或按需重跑）——那是 gate.sh 的改造，不在本步范围。

## 步骤 6 结论：零引用 ≠ 一次性（2026-10-20 实测）

全库扫「文档 / 门禁 / 其他脚本都不出现」的脚本：**16 个**，但只有 8 个是真正的一次性修复件。

**三条判据同时满足才进 `scripts/attic/`**（缺一条就留在 `scripts/`）：
1. 文档（`docs/`、`AGENTS.md`、`README.md`、`.memory/`）与 `gate.sh` 零引用；
2. 名字即用途：`fix_*` / `batch_fix_*` / `simple_fix_*` / `restore_*`；
3. 最近 7 天无改动（证明不是在用的活工具）。

**移走的 8 个**（全部最后改动 2026-10-10）：
`batch_fix_keywords` · `batch_fix_nav_vocab` · `fix_cross_para_quotes` · `fix_missing_vocab_header` ·
`fix_nav_and_vocab` · `fix_quote_block_quota` · `restore_keywords_from_commit` · `simple_fix_keywords`

**留下的零引用脚本**（零引用≠该删，它们是生产工具，只是没被文档点名）：
`build_block_keywords` · `realign_block_keywords` · `rebuild_vocab_tables` · `vocab_list_to_table` ·
`vocab_plan_helper` · `list_advanced_candidates` · `lk_verify_batch` · `block_scope_check`（他实例当日在用）。

⇒ **教训**：原计划写「48 个一次性脚本」是估的；实测 16 个零引用、8 个可移。
**「没人引用」和「没人需要」是两件事**——生产工具常常没进文档（因为它是写的时候临时用的），
按零引用批量清理会把它们一起清掉。

## 步骤 9：脚本准入三条（2026-10-20 立）

背景：30 天内新增 92 个脚本，`scripts/attic/` 堆了 564 个；有本书在执行时自己在书目录里造了
5 个 `.build/*.py`（已 gitignore，属正当脚手架），另有 3 个散落在期刊目录与书目录里（已清）。
脚本库变大的真实原因不是"需要"，是**没有归口、没有退出机制**。

**三条准入**（新增任何脚本前逐条过）：

1. **能加参数就不开新文件**。同一族判据扩展现有工具（`bookform.py` 一个文件干了引语/结构/中文密度/形态四类），
   不要一个缺陷类配一个脚本。
2. **单本书专用的放 `scripts/<书简称>/`**，带 `README.md`；**顶层 `scripts/*.py` 只放跨书复用的工具**。
3. **一次性修复件用完就退场**：移 `scripts/attic/`（gitignored）或直接删；留在顶层等于假装它是长期工具。

**机械守卫**：`python3 scripts/check_rules_health.py` 现在是四类判据——
AGENTS 字符预算 / rules 路由 / 引用不悬空 / **脚本归口**（已入库脚本必须在 `工具登记.md` 里；
书与文档目录不许出现 `.py`，`.build/` 与 `raw-gates` 证据除外）。
**改脚本或加脚本之后跑一次**。
