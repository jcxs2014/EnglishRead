# 20 提交门禁与规则适用范围

> 本文件由 `AGENTS.md` 拆出（2026-10-20，重构第 2 步）。**常驻路由在 `AGENTS.md`，本文件按需读。**
> 拆分基线：tag `rules-refactor-base-20261020`；进度见 `docs/rules/PLAN.md`。

3. **提交门禁（下列全绿）**：书籍批次 commit 前必须依次跑下列检测器，任一 ❌ 回炉后才可 commit：

   ```bash
   # 🚦 先判 lane：有 epub = 完整门禁；无 epub = 降级（部分判定不适用，见下）
   ls "<书目录>"/library/*.epub >/dev/null 2>&1 && echo "完整 lane" || echo "降级 lane"

   python3 scripts/verify_quotes.py "<书目录>" "<该书epub>"                    # 引文逐字（每篇 10/10 ✅）
   python3 scripts/verify_quotes.py "<书目录>" "<该书epub>" --full             # 补一次整串/逐段 flat 比对，关闭 52 字符指纹盲区（**仅取证，不参与退出码**）
   python3 scripts/check_vocab.py "<书目录>"                                   # 词汇表（FAIL=0）
   python3 scripts/check_entities.py "<书目录>"                                # 梗概实体一致性（未知实体=0）
   python3 scripts/corruption_scan.py "<书目录>"                              # 编辑损坏（U+FFFD/双句号）——见下
   python3 scripts/sweep_full.py "<书目录>" --quiet                        # 引语整串 flat 比对（2026-09-27 进门禁）
   python3 scripts/check_chinese_layer.py "<书目录>"                      # 中文层体检（2026-10-19 进门禁，见下）
   ```

   **`check_chinese_layer` 为何进门禁（2026-10-19 实测）**：10 本 2026-10-17~19 完工的书
   **全部通过前 18 lane**（引语逐字 100%、vocab FAIL=0、空段扫描 0 处），
   而「中文理解」有 12%–100% **整段是英文**、「为什么这样写」有 80%–100% 是英文或中英夹杂。
   根因：**前 18 lane 没有一个查分析层**——`verify_quotes` / `check_chapter_quotes` /
   `sweep_full` 只验**引语行**；`check_vocab` 只看**词汇表**；lane ⑱ 块覆盖对账只查
   「每块进没进 verify_quotes」，**不查块里有没有内容**。
   ⇒ **机械层对「分析层是否真的写了、是不是中文」是真空绿。**
   同批实测的三种**假修复**（都被本项抓住）：① 给英文中文理解前面**加「显示」二字**；
   ② 把中文理解里复述的**英文引语删掉**、留下 `——。` 残句（同时踩第 9 条 d2）；
   ③ 「为什么这样写」整段留英文、只报「提示型只记不改」。
   ⚠️ 本项进正门后**已有 150 本存量书 gate 变红**（16 本阻断型 ≥50）——
   那是真实状态不是误报；按「🚦 新规则的适用范围」节，**存量书不自动回溯整改**，
   **新增书籍必须过这一关**。

   **`corruption_scan` 为何进提交门禁**：脚本化行编辑重跑在已替换的行上会复制前缀或从句，而**现有门禁只盯引语行**，这类损坏六道门禁**全部不可见**（实测刚通过全量复核的 3 本书各抓到 1 处 U+FFFD，且 `text/` 侧干净 ⇒ 生成时截断）。**审查期每次批量修复后必跑**——与第 10 条 c 步结构复扫的「修复后」时点**合并执行，不另设检查站**。

   **🚦 lane 决定哪些判定成立**（2026-09-26 实测确立，务必先读）：

   | 判定 | 依据 | 完整 lane | 降级 lane（无 epub） |
   |---|---|---|---|
   | 例句是否命中**本章** | 本章 `text/` | 权威 | **权威，照常判** |
   | 引语是否逐字在**全书** | epub | 权威 | **不出结论**：2026-09-27 已加守卫，无 epub 即**退出码 2 + 「❓ 无法判定」**，不产出计数（此前会报 `0/N（0%）`，**读起来像「全部伪造」而实为「根本没查」**） |
   | 词条是否 A 类虚构 | 全书参考集 | 权威（epub 口径） | **不出结论**，列「❓ 无法判定」 |

   **降级 lane 的书不是"检查通过"，是"部分检查没做"**——报告里必须写清 lane，不得与完整 lane 的数字混用。规模明细与复核更正见 `docs/实测档案/G_第3条_规模实测.md`。
   **🚦 门禁结论必须分四档（2026-09-26 确立三档，2026-10-18 增补第四档「跳过型」）**

   门禁的非零输出**不是同一种东西**，处置也不同：

   | 档 | 处置 | 判据 |
   |---|---|---|
   | **阻断型** | **必须改** | 数字对不上＝内容错了（`verify_quotes` 非 100%／`check_vocab` FAIL／`check_chapter_quotes` MISS／`corruption_scan` FAIL／`check_entities` 未知实体／`audit_numbers` ❌ 差≥2） |
   | **提示型** | **只记不改** | 措辞正当或启发式判的（`audit_numbers` ❓ 未判／`check_vocab` 基础档疑含超纲词（**判据 2026-10-06 已改**：不再单看长度 ≥9，现按 `check_vocab.py:_basic_over_scope`＝短语按成分词逐个判 + 落在 `BASIC_WORDS` 日常表即放行 + ≤8 字放行 + 命中生僻词黑名单才报）／`check_anchor` ⚠️ 松散关键词）**⚠️ 2026-10-19 补硬前提，见下** |
   | **假红型** | **先修工具** | 工具坏了（`缺必备章节` 小样本／`例句未命中本章` 而 `ch_corpus` 为空／`audit_structure` 空跑） |
   | **跳过型** | **先修工具，别当「干净」** | **报告写「0 条／未检出」，但那批内容根本没进扫描集**——不是「查过没查到」，是「没查」。判据：**核对工具实际读了什么，再看它报的数字**（`check_entities` 对 108 本非虚构抽 0 段仍 exit 0／`verify_overview_quotes` 的「无引语行（正常）」把 194 个文件 / 2,277 行带标注引语判成无引语／`check_overview_full` 不认 `## 节点N：（chNN）` 节标题内嵌章号）。**处置同假红型＝先修工具**，但**额外要求把「未核」写进报告**——写「正常」就是把缺账当结清 |

   14 章实测：**阻断型 100% 是真缺陷，提示型 100% 是正当措辞或启发式误报**——**但这个 100% 只有分类之后才成立**；不分类时人会先改提示型（**改坏正当内容**）。逐条案例见 `docs/实测档案/J_第8-10条_案例移出.md` 与 `docs/新书启动模板.md`「每条规则挡住的历史坑」。

   **第二次实测（2026-09-29 五步审查，The Bookshop by the Bay）**：33 处阻断型 / 16 条提示型 / **7 条假红型**——假红型里最要紧的一条是 **`check_overview_full` 的 B 段只验「逐字命中章 == 标注章」，对说话人、人物、关系、结局零覆盖**，而本轮 6 条说话人错配全在其口径外 ⇒ **报告里必须写清「标签对 ≠ 内容对」**。逐条见 `docs/实测档案/M_第10条_五步审查实例与检查器死代码.md`。

   **验收纪律**：**验「已修」要验它被修的那一刻，不是验现在**——「现在没有」不等于「从来没有过」。自查死链/残留时区分「提及某文件」与「指引读者去读某文件」，后者才是活引用。   **报告纪律**：贴门禁输出时**每条标明属于哪一档**；**提示型不阻塞 commit**；**假红型必须先修工具**，不许把它当内容缺陷去「修」md；**跳过型必须改写报告措辞**——把「无 X，正常」改成「**X 未进扫描集，❓ 无法判定**」，否则缺账会以「干净」的形式一路传到完工通报与下一批次（`check_entities` 的「0 个文件存在未知实体」就是这么变成一片绿的，2026-10-18）。

   #### 🚦 提示型豁免的边界（2026-10-19 立；**提示型不是缺陷豁免条款**）

   > **背景**：2026-10-19 全库扫描发现，10 本 2026-10-17~19 完工的书在协作板上自报
   > 「**五步审查通过 · 阻断型 0**」，而实测 45%–94% 的「中文理解」是英文、
   > `bruja-s-nest` 有 94%、「为什么这样写」有 96% 是英文。
   > **它们当时全部通过 18 lane 门禁**（引语逐字 100%、vocab FAIL=0、空段扫描 0 处）。
   > 根因不是门禁坏了，是**第 3 条的四档是为「门禁输出的报警项」分的档，
   > 而中文层退化是「一个成体系整层坏掉的缺陷类」**——拿报警项的分档去处置缺陷类，
   > 于是整层可以一块一块地被降级、最后带病过关。
   > 触发本节的直接原因：**「提示型 = 只记不改」被当成了万能豁免票。**

   **① 提示型有硬前提：「内容本身成立」。**
   「措辞正当或启发式判的」这句话有两个不可分割的前提——**内容本身是对的**，
   只是量具判不准（`audit_numbers` ❓ 未判 / `check_vocab` 基础档疑含超纲词 /
   `check_anchor` ⚠️ 松散关键词，这三条的共性就是**报警指向的内容本身没问题**）。
   ⇒ **内容本身不成立的，一律阻断型**，不得降级为提示型。
   典型：把「中文理解」写成英文、把「为什么这样写」整段留英文——**这不是措辞问题，是内容缺失**。
   （`check_chinese_layer` 已按此把「为什么这样写」整段无中文列为**阻断型**，不再归提示型。）

   **② 对称条款：成片同类报警，**也可能是内容错而不是工具错**。**
   原文只有单向的一句：「大面积同类报警**先假定是自己脚本口径错了**，而不是内容错了」
   （防的是把正当内容改坏）。⇒ **补上反向的一句**：
   **报警连续成片时，先抽 2–3 行读原文判定判据是否成立；若内容确实不成立，
   这是内容缺陷，不得以「工具可能误报」为由搁置。** 两种可能都要排除，不许只查一种。

   **③ 量级条款：提示型占比过高 ⇒ 不得直接申报完成。**
   单条提示型「只记不改」的前提是它是零星措辞问题。**若某一类提示型
   超过本书引语块的 30%**，它就不是「措辞正当」，而是**整层没写**
   （实测 `armor-for-liars` 854 条 / 472 块 ＝ 平均每块 1.8 条）。
   ⇒ **此时必须先抽样 20 条人工定性**（是正当措辞还是没写），把结论写进报告，
   **才可申报完成**。**不许用「提示型只记不改」直接结清。**

   **④ 基线对账：报「已修」必须给「修复前 → 后」，不接受只报当前值。**
   「验「已修」要验它被修的那一刻」的对称面：**「现在阻断型 0」也不等于「每个块都被修过」**。
   ⇒ 修复类任务的报告必须给出**修复前后的数字对账**（如「英文理解 146 → 0」），
   并说明**改写方式**（重写 / 翻译 / 补写）——**只报「0」与「没查」在文本上无法区分**，
   这与 `verify_overview_quotes`「无引语行（正常）」把 2,277 行带标注引语判成无引语是同一种病。

   **⑤ 分档可被推翻：执行方不得单方终局裁定。**
   本节只规定了「审查方复核报警同样按四档分类」和「不分类就照单全改」，
   **没有规定执行方自报的分档可以被推翻**——缺口就在这里（协作板上 8 本书
   自报「五步审查通过 · 阻断型 0」而实际整层是英文）。
   ⇒ **执行方自报的分档，用户与异实例均可推翻**；推翻后按第 10 条走。
   协作板上的「五步审查通过」**不是终局**，它是一次申报。

   **⑥ 缺陷类要按类处置，不按报警项处置。**
   一整层退化（分析层没写）**不能拆成若干个「提示型报警项」结清**——
   报数时必须写「**中文理解纯英文 XX → 0**」这样的**类级对账**，
   而不只是「阻断型 0、提示型 N」。**类级对账才是真账。**

   **⚠️ 「大面积同类报警」先读行复核，再批量改**：检查器报出**成片同类错位**时，**先假定是自己脚本口径错了，而不是内容错了**（Such a Fun Age 实为 19 条标注全对）。① 先 `sed -n` 读 2–3 行确认判据；② 确认是脚本问题就**先修工具再重跑**，不动 md；③ **一次改 10+ 处同类内容前，先只改 1 条验证判据成立**——与第 10 条 a 同源，防「修」本身成为缺陷源。

   有 text/ 逐章提取件的批次，加跑 `check_chapter_quotes.py` 逐章严格校验（引语必须命中**该章自己的**提取件，防跨故事搬句）。
   总览文件（概述/金句精选/情感节点）不在 verify_quotes 主口径内，须单独加跑 `python3 scripts/verify_overview_quotes.py "<书目录>" "<epub>"` 验证总览引语。
## 🚦 新规则的适用范围（2026-10-18 用户拍板；**唯一副本**）

> **拍板原话**：「我觉得新的规则不用再回头去影响已完成的书籍，只针对新增的书籍……不然需要改动的范围太大了」
> ——采纳时补一句限定：这条管的是**判据变更**，管不了**工具失准**（见下表第二行）。

**分三类，别一刀切**：

| 类别 | 本库实例 | 回溯重跑 | 回溯改 md | 为什么 |
|---|---|---|---|---|
| **判据变更**（政策改严/改口径） | D1 块数改「同书自校准」· `--wide` 转默认（若采纳）· `check_quote_order` 进 gate lane | — | ❌ **只对新增书籍** | 回溯＝为新政策返工旧交付物，**且常是倒退**（D1 会让 31 本越界重排块序，而 `burn-for-you` 本书中位 3 块很可能就是体裁使然——那不是缺陷） |
| **工具失准**（工具一直声称要做、实际没做到） | `check_entities` 相邻梗概标题丢整节（投毒抓出）· `check_nav_layer` 分节吞并 | ✅ **精准重跑受影响的书并留档** | ❌ 不自动改 | **这不是「新规则」，是工具 bug**：那些书当年报告里的「✅」本身是假的。不重测，历史结论永久不可信 |
| **只报不判红**（显式化但不进退出码） | 章节覆盖反向对账 · `--wide` 取证 | ✅ 随手跑 | ❌ 不自动改 | 零判红成本，读一眼报告即可 |

**三行规则**

1. **判据变更只对新增书籍生效**；已完工的书**不自动回溯重判、不自动回溯改内容**。
   真在老书上手动修，改的是那本书，不是本条。
2. **工具失准必须重跑并留档，但只跑「受影响的书」，不是全库**（落点见下），
   **且重跑结果不自动触发整改**——出了真缺陷逐本单独决定修不修。
   留档的意义是「这些书在当前工具下是什么状态」可查，而不是「老书都得返工」。
   - ⚠️ **精准重跑 ≠ 回溯整改**：2026-10-18 本轮精准重跑**顺手抓出两条此前 18 lane 全绿、
     `verify_quotes` 报 100% 的真实内容缺陷**（`sweet-fury` ch10 引语把叙述者的概括句删掉、
     接上下一段内容拼成一条原文不存在的「连续引语」且未标 `…`；ch15 分析层行内引语删了
     `She's` 与人名）。**这类发现只留档、不自动改**——按上条逐本由用户决定修不修。
   - **误报率高的工具不进回溯范围**（见下条）。
   - **「受影响」的判定方法（唯一口径，两步）**：
     ① **基线取修前的那一版**：`BASE=$(git log -1 --format=%H -- scripts/<检查器>.py)` 再
        `git rev-parse $BASE^` 与 `git show <base>:scripts/<检查器>.py`，
        把旧版落成临时脚本，与当前版**跑同一批书**，逐书比退出码＋明细。
        ⚠️ **不能用 `git show HEAD:`**——修复一旦 commit，HEAD 就是**修后**版本，
        比对结果必然是「0 本受影响」（**2026-10-18 实测踩到**：本轮真实受影响 17 本，
        用 HEAD 当基线算出 0，照它留档会把真受影响的书写成「没变」）。
     ② **再从「输出有差异」收窄到「明细真变」**：汇总行修正（如修掉 `⚠️` 与阻断计数双算）
        与**新增只报不判红行**也会造成全文差异，但**判定没变**。
        只有 `❌` 明细条目增删的书才算受影响——本轮 341 / 384 本「输出有差异」里
        **只有 17 本明细真变**，其余全是汇总行与只报行变化，留档只会产出几百个空结论。
   - ⚠️ **2026-10-18 修正**：本条原写「全库重跑」，实测会**一次产出 429 个留档文件**，
     而 `.memory/raw-gates/` **并不在 `.gitignore` 里** ⇒ 这些文件全部进 `git status`，
     在本机「多实例共用目录、禁 `git add -A`」的红线下**本身就是误提交风险**
     （实测当时 `git status` 有 288 行 raw-gates）。用户 10-18 明确要求改为精准重跑。
   - **误报源不进回溯范围**：`verify_fragments_indep.py`（假红 93.5%）·
     `check_quote_order.py`（会让 341/483 本变红）——这类工具跑全库基线只会**制造几百本噪声**，
     噪声要消耗人逐条分辨，比不回溯更贵。它们的结论写进 `docs/实测档案/`，**不生成基线文件**。
3. **返修书按「改动即适用新规则」**（touched-on-write）：老书再次被打开、改了哪部分，
   哪部分按**新规则**核。不因为它「是老书」就永久冻结，也不因为它「改过」就整本重判。

> **为什么不给工具加「这本书是不是新的」判断**：487 个书目录逐个标注太贵，
> 且每个工具各判一次必然漂移（同一次运行里两工具对同一本书给出相反的「新旧」结论）。
> ⚠️ **禁止让工具自己推断「这本是不是新书」**——这是第 2 类（第 8 条）那种
> 「拿自己的口径当事实」的变体。
