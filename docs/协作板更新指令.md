# 更新自己那条协作板 / 工作日志条目

> 复制下面「指令」整段，粘进你的会话即可。所有步骤都由 `scripts/post_collab.py` 执行，
> **不要手写板消息抬头**（身份与时间戳由脚本查登记表生成，手写就是「身份混乱 + 捏造时间戳」的来源）。

---

## 一句话指令（最简版）

> **用法**：要发板 / 写日志时，复制下面这段填空后发给 agent。
> 它只是**入口**——六步细节、七条硬约束、阈值与假红说明全在本文档下方，agent 必须读完再动手。

```
按 docs/协作板更新指令.md 更新我的协作板与工作日志条目（身份 <写法>，目标 <书名>，类型 <完工 | 审查结论>）：
一律走 python3 scripts/post_collab.py（**勿手写抬头**），写完跑 verify --book "<书名>" 与
python3 scripts/check_collab_guard.py，两者全过后只提交 COLLABORATION.md 与 .memory/daily/YYYY-MM-DD.md（**不 push**）。
```

**为什么只写这么短**：指令是复制粘贴用的，只填「身份 / 目标 / 类型」三个变量；
其余（`--at` 用**完工时间**而非发帖时间、审查结论用 `--append` 就地并入、正文 ≤20 行 / ≤5000 B、
每书一条、上限按**追加后整条**算……）由 agent 从本文档读取——**理由与口径写在块外，不塞进指令**。
**简化的是入口，不是门禁**：本文档下方的七条硬约束与六个步骤一条都没少。

> ⚠️ **`check_collab_guard.py` 退出码 0 的覆盖面有限（2026-10-17 审计，与 AGENTS.md 同一处）**：
> 该守卫只做**三项硬判定**——模板头 5 项标志齐全 · 消息数没减少 · 抬头未被手改重复（另加首行标题）；
> **「时序」那一条是 `print` 出来的提示型、不进 `bad`、不判红**，而且只比**首两条**——
> 板中部的乱序它根本看不见。
> （2026-10-17 同步：原式 `(\d\d:\d\d)` 只取时分、丢掉日期段，跨日一律误报「可能未按最新到最旧插入」，
> 10-05 / 10-07 两次人工判定因此无工具背书、白查一轮；已改为日期+时分一起比并兼容双时间抬头
> `[发帖时间 / 完工时间]`。）
> ⇒ **退出码 0 只证明「没把板写坏」，不证明「排序对 / 阈值合规 / 没超行超字节」**；
> 后者由第 1 步的 `check`（超行超字节两维都判）与 `verify` 负责，另加逐条回读。

## 六步详版指令（复制这一段）

```
用 scripts/post_collab.py 更新我自己的协作板与工作日志条目，按下列顺序执行，不要跳步。

0. 认领身份并盘点我名下条目（不确定叫什么就先跑一次，从候选里挑已登记的写法）：
   python3 scripts/post_collab.py mine --me "<你记得的任何写法>"   # 列出我发过的全部条目（含历史别名）
   python3 scripts/post_collab.py check                            # 全板体检；行数与字节两维都判

2. 把要发的内容写成**纯正文**（不要写 `### [时间戳] [身份]` 抬头，脚本会生成），
   存成一个临时文件，例如 /tmp/collab_body.md。
   板消息只放：文件数 · 门禁数字 · 结论 · commit 计数 · 一行日志指引，**正文 ≤20 行**
   （行数是主要信号；**口径＝只算你写的那段正文**，脚本自动生成的抬头与条目间空行不计，见下面「长度口径」）；
   字节阈值 5000 B 是**失控兜底**，不是第二道门槛——见下面「体检别人的板」。
   逐行原始输出、**四档定性**（阻断／提示／假红／跳过，见 `docs/rules/20-gate.md`）、
   原文行号、逐条清单属于工作日志，不属于板。

3. 更新协作板。**首次完工**才新建，给 --at「<完工时间>」；审查结论用 --append 就地并入，
   **不给 --at、标题一字不动**（审查时间写进正文那一行）。
   ⚠️ **上限按「追加后的整条正文」算**：完工那条已占掉一半额度，审查结论若撑破 20 行会被拒——
   此时把两段**合并压缩**后用 --replace 整体重写（完工时间仍不动，两段都必须保留）：

   python3 scripts/post_collab.py board /tmp/collab_body.md \
       --book "<书目录 slug 或书名>" --me "<写法>" --at "<完工时间 YYYY-MM-DD HH:MM UTC>"   # 首次
   python3 scripts/post_collab.py board /tmp/collab_body.md \
       --book "<书目录 slug 或书名>" --me "<写法>" --append                                  # 审查结论
   python3 scripts/post_collab.py board /tmp/merged.md \
       --book "<书目录 slug 或书名>" --me "<写法>" --replace                                 # 合并压缩

   ⚠️ **不是某本书的事件（板级自查 / 工具变更 / 规则调整）把 `--book` 换成 `--topic`**，
   口径与日志侧开节方式见下方「跨书主题」节——用错参数会被判成「新书」而另开一条。

4. 更新工作日志（**默认**就地并入该书当日条目，直接 --append）：
   python3 scripts/post_collab.py daily /tmp/collab_body.md \
       --book "<书名>" --me "<写法>" --append

   ⚠️ **非书主题用 `--topic "<【…】>"`**（脚本会自动补 `## 【…】` 标题，见「跨书主题」节）。

   ⚠️ **一本书当天只应有一个专节**（见下面「每书一条」那节的定义）。同一本书
   散在多个 `##` 节里，后来者不知道该看哪条——这是硬约束，板与日志各自成立。
   已经散开的先合并：完工在前、审查在后，按时序排成连续的一节。

   ⚠️ **日志的「节」只认 `## ` 二级标题，`### ` 不算开新节**（2026-09-29 定）：
   - 书当天还没写过（`--book` 零命中）时走新建分支，**脚本自动补 `## <书名>` 标题**，
     正文不用自己写；自己写了 `## ` 就以你写的为准。
   - **绝不要用 `### ` 给一本书开档**：它不切节，那段会算进**上一本书**的节里。
     实测：The Last Lifeboat 的审查明细 56 行用 `###` 写在《The Cafe at Beach End》
     节下，`verify` 一直按后者统计。
   - daily 是长期存档档，**不设行数上限**；板上那 20 行 / 5000 B 只管板消息。

5. 写后自查（**必做**，脚本返回 0 也要跑）：
   python3 scripts/post_collab.py verify --book "<书名>"
   # 期望：板恰 1 条 ✅、当日日志该书专节 ≥1 ✅（**1 节才是目标，>1 说明该合并**）；退出码 0
   git diff --stat COLLABORATION.md .memory/daily/
   # 板有 >1 条时**不要去删别人的**——把自己的那条 --append 补齐即可。
   # 日志里 >1 个专节同理：自己造成的就自己合，别人造成的在板上留一条说明。

6. 提交时只 add 自己那两个文件（**raw-gates 原件不在此列**，见下方说明）：
   git status --short COLLABORATION.md .memory/daily/    # 确认本次只有这两个文件在改
   git status --short                                    # 看第二列：暂存区可能已有别人 add 的文件
   git add COLLABORATION.md .memory/daily/YYYY-MM-DD.md
   git commit -m "docs(协作/日志): <书名> <完工|审查结论> 就地更新" -- COLLABORATION.md .memory/daily/YYYY-MM-DD.md
   # git 四条红线（`-m` 写在 `--` 前 / 只 add 自己路径 / 禁 amend / 不擅自 push）见 AGENTS 顶部。
   # 发板前若跑过门禁，再补一次「漏提交检测」——原件与 md 同批入库：
   git status --short .memory/raw-gates/<slug>/   # 零 ?? = 完整（只管本次该产出的那几件）
```

> **步骤 6 的两点说明**：
> ① **raw-gates 原件不属于这条「只 add 两个文件」的禁令范围**——那条管的是**本次发板改动**只含那两个文件。
> 门禁原件是**另一批产物**，规则是「**与产出它的那批 md 同批提交**」（做法与理由见
> `docs/新书启动模板.md` 的「原始输出全量留存」条）。上面最后那行与模板第 4 条的
> **「漏提交检测」是同一件事**，切勿当成两项检查——模板那条是**写作者视角**、这里这行是
> **发板者视角**的补做，**判据与命令完全一致**。
> ② 判据是**零 `??`**（不是数文件个数——历史计数每天都在漂）。若发现本任务 raw-gates 目录下
> 仍有未追踪件，说明当时漏了，**回头单独补一个 commit 补上**（补交也要写明是哪几件，
> 便于后来者核对完整性）。
> 2026-10-01 实测：**多本书的整批审查原件（a–e 全套）漏网**，而它们的 md 与协作板/日志都已入库
> ⇒ **md 全绿会掩盖原件的缺失**。这正是「漏提交检测」此前只查 `<书目录>`、不查 `.memory/raw-gates/` 造成的盲区。

## 跨书主题：用 `--topic` 代替 `--book`（2026-10-18 补）

板与日志都是「每书一条」，但**板级自查 / 工具变更 / 规则调整 / 身份事故**这类事件
本身涉及多本书（本节下方「每书一条在日志侧怎么算」也承认它们存在），**无处挂在某一本书下**。
这类条目用 `--topic`：

```bash
python3 scripts/post_collab.py board /tmp/topic_body.md \
    --topic "【工具变更】" --me "<写法>" --at "<完工时间 YYYY-MM-DD HH:MM UTC>"

python3 scripts/post_collab.py daily /tmp/topic_body.md \
    --topic "【工具变更】" --me "<写法>" --day YYYY-MM-DD
```

**四条口径**（都出自 `scripts/post_collab.py`，不是约定）：

| 口径 | 实现 | 含义 |
|---|---|---|
| **topic 直接顶替判重键** | `:260` `if a.topic: a.book = a.topic` | 「每书一条」自动变「**每主题一条**」；`:305` 的拒绝话术也跟着换成这五个字 |
| **正文必须含 topic 原串** | `:291` `if a.book not in body` | 连 `【】` 整个原串。正文首行写 `## 【工具变更】…` 最稳（日志侧自带 `## ` 标题会被原样保留，见 `:409`） |
| **日志自动开节的标题跟着变** | `:411` `body = f"## {a.book}\n\n" + body` | 用 `--topic` 时脚本补的是 `## 【工具变更】`，**不是书名**——所以别再用 `--book` 硬塞 |
| **判重键＝标题，不是全文** | `_topic_is_title()`（`_book_hit` 的 topic 分支） | 主题串须出现在该条的**前两个非空行**之一才算「这条的主题是它」（板：第 1 非空行是自动抬头、第 2 行才是你写的标题；日志：第 1 行就是 `## 【…】`）。**正文里提一嘴不算**——2026-10-18 修，之前会把交叉引用误算成本主题的条目 |

⚠️ **topic 复用会撞 20 行上限**：同主题第二次发（`--append`）按「**追加后整条**」算。
原条目已接近 20 行时，**换一个新前缀**比硬压省事（实测 `【门禁修正】` 已占 19 行 ⇒
另开 `【门禁修正·C/D】`）。但**别为了绕上限把同一件事拆成两个 topic**——那等于放弃「每主题一条」。

⚠️ **topic 前缀要能自解释**：板与日志上先后出现过 `【工具变更】`、`【门禁修正】`、`【工具盲区】`、
`【规则调整】`、`【规则同步】`、`【身份更正】`、`【期刊工具】`、`【notes1 切割】`、`【指令文档】`、
`【适用范围】`、`【文档同步】` 等。新前缀先 `grep '^## 【' COLLABORATION.md` 看有没有同义的，
**同义就别造第二个**；⚠️ **上面这份清单不是全集、别照抄**——它会漂，**以 `grep` 输出为准**。

✅ **跨条目互引可以放心写完整的 `【…】` 串**（2026-10-18 已从根上修掉）：
上一版本 topic 判重是**在整份文件里找 topic 原串**，不区分「本条目的主题」与「正文里提到的
别的主题」——实测在 `【适用范围】`/`【门禁修正】` 两条里写了「详见【文档同步】」之后，
新建 `【文档同步】` 被拒收（报「已有 **2 条**条目」，而那 2 条正是这两处指针）。
现在判重改看**标题**（见上表第四行），正文里的交叉引用不再影响判重。
⚠️ 该修只覆盖 topic：**书名侧仍是「标题行 → 标识行 → 整条子串」三层回落**，
最后一层仍分不清「关于该书」与「句中提及该书」，故 `--replace`/`--append` 命中他书节时
仍会打一条「可能是别的书的节」的 ⚠️ 要求人工核对——**那条提示是书名的防线，不要关掉**。

## 七条硬约束（脚本会拒，但你也该知道为什么）

| 约束 | 拒收时的原话 | 由来 |
|---|---|---|
| **板消息正文 ≤20 行 / ≤5000 B**（**按追加后的整条算**；口径见下节） | 「板上只放：文件数 · 门禁数字 · 结论 · commit 计数 · 一行日志指引」 | 2026-09-28 实测：板上 48 条里 19 条超线、占全板 56%；**其中 11 条正是「完工+审查」并条撑破的** |
| **每书一条**（板与日志各自；用 `--topic` 时变成「**每主题一条**」） | 「请用 --append 就地并入既有条目」 | 同一本书被完工通报、审查结论分开发两条，后来者找不到该看哪条 |
| **正文必须逐字含书标识 / topic 原串**（`post_collab.py:291` `if a.book not in body`） | 「正文里找不到书标识「X」——判重与写后自查都靠它」 | **判重与 `verify` 都靠这个字符串**：正文里没有它，脚本会以为「没发过」而允许新建第二条。⚠️ 用 `--topic` 时必须是 **topic 原串（连 `【】` 一起）**，少一个括号也拒收——本轮实测改了两遍才发出去 |
| **不得改他人消息** | 「该条目不属于 X——不得修改其他实例的消息」 | 2026-08-31 ZCode-Mac 误改 Opencode-Mac 的合法消息 |
| **抬头时间＝完工时间，不是发帖时间** | 「新建板消息必须给 --at」 | 板上按完工时间排序；代理往往隔天才补报，按发帖时间排会乱序 |
| **追加不改标题** | 追加路径不生成抬头，原样保留 | 审查结论的时间写进正文，完工时间不动 |
| **正文里不许自己写抬头** | 「身份与时间戳由本脚本生成」 | 2026-08-31 还捏造过时间戳（实际 10:59 写成 11:20） |

### 「每书一条」在日志侧怎么算（2026-09-29 补）

板上一条 = 一条 `### ` 消息，日志里一条 = **一个 `## ` 二级标题的节**。
但日志里有一类节是**跨书混合节**——板级自查、工具变更、身份事故这类事件本身
涉及多本书（如「协作板自查：板上 8 条消息」「我的协作板条目归属误判」）。
所以判「该书有几条」不能只看正文有没有出现书名：

| 判据 | 含义 | 用在哪 |
|---|---|---|
| **专节** | `## ` 抬头**点名该书**的节 | 计数「该书有几条」**只看这个** |
| 顺带提及 | 跨书混合节正文里提到该书 | **不算**它的条目 |

⚠️ **为什么必须分开**：2026-09-29 实测，若按「正文出现即命中」计数，
`The Lonely Hearts Book Club` 命中 2 节、`I Have Some Questions for You` 命中 2 节
——多出来的那节都是跨书节（板级自查）。当时据此把写后自查放宽成「≥1 节」，
结果**「每书一条」在日志侧被废掉**，而这正是本条硬约束要防的事（放宽的是症状不是病根）。

**目标状态**：该书的专节 **= 1**，且**连续**。完工在前、审查在后。

> ⚠️ **脚本现状与本节目标的差距（2026-09-29 补，同日再补板侧/日志侧假红与输出矛盾）**：`verify` 目前只报
> 「≥1 个专节」，**不会**因为 >1 而报 ❌；`--append` 命中多个专节时取**第一个**。
> ⇒ 上面这些目前是**人工纪律**，不是脚本门禁。合并前先用
> `python3 -c "…_log_sections…"` 之类看清有哪几节（抬头点名该书的那些）。
>
> **板侧与日志侧另有两处已知假红（2026-09-29 修复 `a07a2ce8` 误删事故时撞上）**——
> **`verify` 报 ❌ 不等于真有多条，别照着去删别人的**：
> - **子串计数分不清「关于该书」与「提到该书」**（板侧判据是 `book in entry`）：
>   事故说明、他人条目里引用本实例的记录都会命中。The Green Road 实测报 **3 条**，
>   真条目只有 **1 条**，另 2 条是合法提及（其中 1 条早于该次事故就已存在）。
>   ⇒ **要判「真有几条」，看条目正文首行是否为 `**《书名》…`**，不要看 `verify` 的数字。
> - **日志侧把日期硬编码为「今天」**（`verify(book, date.today())`）：跨天补记的书
>   永远报「0 个二级节 ❌」。The Green Road 专节在 09-27，当天日志 0 节属正常。
>   ⇒ **跨天补记时以「`## ` 抬头点名该书的专节数」为准**，此时 `verify` 的日志侧数字不成立。
>
> ⚠️ **另有一处工具输出与本节目标自相矛盾**：`verify` 在日志侧 >1 节时会打印
> 「同书多节＝当天完工与审查各一节，**正常**」——**这与上面「专节 = 1」的目标相反**，
> 照它做就是不合并。**以本节的目标状态为准，忽略那句「正常」。**

## 三个实测踩过的坑

1. **「打印了成功」不等于文件改了。** 替换多段内容时若把 `open(w)` 写在循环外，循环中途抛异常
   就会「什么都没改、但已打印成功」。**第 5 步的自查不是形式**。
2. **返回非 0 时文件也不该被动过。** 工具已改成先在内存里断言、通过才落盘；但你自己写脚本
   改共享文件时同样要遵守，否则会出现「工具说失败、内容却在」的半成品。
3. **别用 `mine | grep 书名` 做自查**——`mine` 只列抬头，书名在**正文**里，这个 grep 恒返回 0，
   agent 会误判成「更新失败」。用 `verify` 子命令（见步骤 5）。
   这条是本指令初版自己踩的：文档写好后照着走一遍，当场发现自查命令返回 0。

## 想新增自己的身份

编辑 `scripts/collab_identities.json` 加一条 `canonical`（统一用 `<名字>-Mac` 或工具名，
不要再造后缀变体）。已知的其他写法放 `aliases`；只是猜测、放 `inferred_aliases`
（用它发消息会打告警提示你去确认）。macmini 那台机器统一加 `-Mini` 后缀。

## 体检别人的板

`python3 scripts/post_collab.py check` 只报告、不改动。**不要去改别人的条目**——
即使发现超长或有错，那也是他们自己该改的；要指出问题就在自己名下另发一条说明。

⚠️ **两个阈值不是平级的**（2026-09-29 实测后重定，字节 2500 → **5000**）：
**行数数「要读几件事」，是主要信号**；字节数在本库（CJK 1 字 3 字节）只反映**写得密不密**，
惩罚密度会**误伤结构良好的紧凑通报**——原 2500 B 时，全板 40 条行数达标的条目里有
**8 条被字节判超**。实测分布：行数达标者**最大 4,359 B**，真正的失控条目**最小 6,029 B**，
**5,000–6,000 之间没有任何条目** ⇒ 阈值落在这道空隙里，上调后误判从 8 条降到 1 条，
而 6,029 B 以上那些真正难读的仍被抓住。

它按**与写入同一把尺子**判：行数与字节任一超即 ❌，并注明超的是哪一维
（`← 超行、字节` / `← 超字节`），摘要给 `超线 N 条（行 x · 字节 y）`。
⚠️ 2026-09-29 之前它**只判行数**，漏报了「行数达标、字节超限」的那一半——
**体检与写入口径不一致时，体检漏报的恰是「写不进去却看不出来」的那一半**。
看到 `❌ ← 超字节` 而行数达标，不必怀疑工具：**两条都是硬约束，只是先撞上了字节那条**。

### 长度口径：只算正文（2026-09-30 统一）

**口径 = `count_text(entry_body(x))`：只算你写的那段正文**，脚本自动生成的
`### [完工时间] [身份] → 收件人` 抬头（含其后的空行）与**条目之间的分隔空行**都不计入。

此前**同一份内容在三个地方量出三个数**（两处都"没写错"，只是各数各的）：

| 量法 | 位置 | 对「正文 18 行」读作 |
|---|---|---|
| 裸正文 `body.count("\n")+1` | 写入端门禁 1（拼抬头之前） | 18 行 |
| 拼上抬头后再数一遍 | 写入端门禁 2 | **20 行** ← 实际生效的放行线 |
| `board_entries` 切片 | `check` 体检 | **22 行 ❌** |

实测（同一份 body.md，阈值 20 行）：

```
改动前   正文 12 行 → 写入端放行 14 行 / 215 B   体检端 16 行     ❌ 两把尺子
改动前   正文 18 行 → 写入端放行 20 行 / 293 B   体检端 ❌ 22 行   ❌ 两把尺子
改动后   正文 12 行 → 写入端放行 12 行 / 163 B   体检端 12 行     ✅ 一致
改动后   正文 20 行 → 写入端放行 20 行 / 267 B   体检端 20 行     ✅ 一致
```

⇒ 修前「照写入端的 20 行写」会**稳定**产出体检红条，真实安全线被压到正文 **17 行**
（16+4=20 压线、17+4=21 ❌）——一把尺子两个刻度，且写入端与体检端**都没报错**。
先落盘的条目因此背上「体检说超线、写入说没超」的悬案。

**现在的安全线就是正文 20 行**（字节 5000 B 仍为失控兜底）。若你仍按 16 行压，
那是把旧口径的余量当成了规则——`check` 的数字已经不再多算那 4 行。
