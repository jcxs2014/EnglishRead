| `audit_numbers.py` | **计数断言核查**（P1）：「N 个词 / N 次 token / N 个分句 / 字符数 / 分隔线切为 N 段」 | `python3 scripts/audit_numbers.py "<书目录>" [--quiet]`。计数断言是本库最高频的语义缺陷（attic 自记），而**现有门禁完全不看分析层**。**但只有两类真有客观真值**：`分隔线切为 N 段`（真值 = 本章 `text/` 的 `^—$` 行数）与 `N 次 <token>`（token **逐字在块内引语里**才判）。**「N 个词 / N 个分句 / 字符数」一律不判，只列未判**——本库这类断言绝大多数指**引语里的某个子短语**而非整条，而那个子短语无法机械定位：实测 `「五个词」` 整条引语 10 词但 `steady as a forest pond` 恰 5 词、`「六个词」` 整条 11 词但 `finish-homework-before-going-to-parties` 恰 6 词、`「三个分句」` 按逗号切得 6 按句号切得 1。**教训：能定位到「数的是哪一个」才谈得上核查。** 年龄/百分比**只统计不判**（需故事事实，文本层推不出）。11 本实测：断言 1473 条 → ❌ 5 / ⚠️ 24 / ❓ 未判 572 / ⚪ 不可核 775。**实现坑**：① 中文后的 `\b` 不可靠（`词\b` 在 `词。` 上不匹配），须用 `(?!\w)`；② **不要用 `(%s)` 直接插值数字字符集**——`+` 会落进方括号变成字面量、量词失效、**静默一条不报**；须用预置的 `NUMC = '[' + NUM + ']+'`；③ `\b` 换非捕获组后没有 `group(2)`，报告行取单位要从 `group(0)` 切；④ `N 个 a / b / c` 是**多 token 列表**须逐个计数求和，token 末尾的 `…` 要剥掉；⑤ `>` 元数据引用块（`作者：`/`原书`/`精读目录`）不是引语，当成引语会让后续断言全拿书目当参照 |

## post_collab.py 长度门禁未按 mode 分流（2026-09-29 修，缺陷由另一实例发现）

**症状**：`daily --append` 对**任何 >20 行的既有节**一律拒收，报错文案却是板口径
「请用 --replace 整体重写」——对 47 行的存档节，那条建议会把存档压没。
绕法只有两个，都很坏：手工行级 Edit；或给 `--limit` 传一个大数（等于把板门禁也一起关掉）。

**根因**：`if hit and (a.append or a.replace):` 这块**没有 `and a.mode == "board"`**，
而紧邻的身份检查（`if hit and (...) and a.mode == "board"`）有 ⇒ 同一函数里一处记得分流、
一处忘了。板上 20 行/5000 B 的阈值因此被套在 daily 的长期存档档上。
实测规模：当日日志 **140 节里 52 节永久无法 --append**。
更荒唐的是**「新建」分支（`hit` 为空）整块跳过这道门** ⇒ 能不能写入取决于
**书名有没有被别处提到**，与内容长度无关。

**同源的第二处**：`_log_sections` 按 `^#{1,3} ` 切节，一本书只要自己带 `###` 子标题
就被切成 N 节 ⇒ `hit[0]` 静默取第一节（追加落到哪节取决于书写顺序），
且写后自查按节计数，同一本书本来就 >1 节 ⇒ **daily 追加一律被拦**。
实测：`Lonely Hearts` 命中 4 节、Cafe 3 节、Paris Deception 3 节。
**长度门禁修了它也不通**——必须连它一起修，否则 daily 仍然不可用。

**修法（三处，板的行为一字未改）**：
1. 合并后长度门禁加 `a.mode == "board"` 条件；daily 改用**净减守卫**（见下）。
2. `_log_sections` 只认 `^## ` 二级标题，子标题归节内内容 ⇒ 分节 140 → 19（= 当日书数）。
3. `_postcheck` 的「恰 1 条」只对 board 生效——日志里一本书当天本来就有多个二级节
   （完工一节、审查一节），套板的约束是错的。`verify` 的日志计数同步改口径。

**净减守卫（新增，替代 daily 的行数门禁）**：`daily --replace` 只换正文、抬头自动保留，
所以新正文必须自带原内容——实测真出过 **387 行完工记录被 132 行新片段覆盖**。
现在净掉 30% 或 20 行以上即拒收，`--force` 可强推。**这才是 daily 该有的门禁**：
不是「别写太长」，是「别把存档写没了」。

**回归套件** `scripts/test_post_collab.py`（8 例，含「板门禁未被放松」与
「--force 强推」两条）。隔离办法：在临时目录建**自带 git 基线**的仓库副本
（门禁 3 会查 `git log -1 -- <file>`，副本必须在 git 仓库里），
用 `POST_COLLAB_BOARD` / `POST_COLLAB_LOGDIR` 两个环境变量指路径——
为此把 `BOARD`/`LOGDIR` 从硬编码常量改成 `os.environ.get(默认值)`，**默认行为不变**。

⚠️ **写这类回归时的两个坑**：① 用**真实数据**当锚点时，书名会在多处出现而命中多节，
测试会因分节缺陷假失败——挑一个只出现一次的字符串（本次用目录 slug）当 `--book`；
② 板上有**两道**长度检查（片段自身的「门禁 1」在 `hit` 判定之前、合并后的门禁在后），
只测其中一道会以为另一道失效——8 例里两种都覆盖。

## post_collab.py 长度口径三处不一致（2026-09-30 修）

**症状**：「照写入端的 20 行写」会**稳定**产出体检红条。实测正文 18 行 ⇒ 写入端放行
（报 20 行）、`check` 报 **22 行 ❌**；反过来，体检显示 20 行的条目正文其实只有 16 行。

**根因**：同一份内容在三个地方量出三个数——**三处都没写错，只是各数各的**：

| 量法 | 位置 | 「正文 18 行」读作 |
|---|---|---|
| 裸正文 `body.count("\n")+1` | 写入端门禁 1（拼抬头之前） | 18 行 |
| 拼上自动抬头后再数一遍 | 写入端门禁 2 | **20 行** ← 实际生效的放行线 |
| `board_entries` 切片 | `check` 体检 | **22 行 ❌** |

切片天然带「本条抬头 → 下一条抬头」之间的**分隔空行**（2 个 `\n`），自动抬头自己又是
2 行 ⇒ 与裸正文**稳定差 4 行**。护栏两端都不报错，于是先落盘的条目背上
「体检说超线、写入说没超」的悬案，运维的人只好把安全线手动压到**正文 17 行**。

**实测对照**（同一份 body.md 喂给两个版本，阈值 20 行 / 5000 B；旧版取自
`git show HEAD:scripts/post_collab.py`，全部在临时副本里跑、真实板零改动）：

```
改动前   正文 12 行 → 写入端放行 14 行 / 215 B   体检端 16 行       ❌ 两把尺子
改动前   正文 18 行 → 写入端放行 20 行 / 293 B   体检端 ❌ 22 行     ❌ 两把尺子
改动后   正文 12 行 → 写入端放行 12 行 / 163 B   体检端 12 行       ✅ 一致
改动后   正文 20 行 → 写入端放行 20 行 / 267 B   体检端 20 行       ✅ 一致
```

**修法**：新增 `count_text(t)`（先 `rstrip("\n")` 再数）与 `entry_body(entry)`（剥自动抬头），
**写入端与 `check` 共用 `count_text(entry_body(...))`**；并**删掉写入端「拼完抬头再数一遍」
的第二道门**——重复门禁正是三处口径的来源（量的是同一份正文，却多算了抬头 2 行）。
`daily` 的净减守卫同步换成同一口径。全板复跑：57 条不变、超线仍 1 条（那条 50 行的真失控条目），
其余每条较旧口径降 4 行。

**为什么不取「切片的数」当统一口径**：那等于把虚高的尺子固化下来，安全线仍是正文 17 行，
运维的人还得继续按 16 行写。统一到「只算正文」才能真正回到 20 行。

⚠️ **回归套件同日一起修（否则看不出改动是否成立）**：`test_post_collab.py` 把日志文件名
硬编码成 `2026-09-29.md`，而脚本按 `date.today()` 取路径 ⇒ 跨天后 daily 的 7 个用例
**整体假红**（`❓ 从未提交过——无基线可比对`、退出码 2），现象与「脚本改动把 daily 搞坏了」
一模一样。改为**文件名用今天、内容取固定样本**（③⑥ 的锚点「节112 / 521 行」依赖样本结构）。

### ① 基线门禁的鸡生蛋——「新一天第一条日志」写不进去（每天必踩）

```
❓ .memory/newday/2026-09-30.md 从未提交过——无基线可比对     退出码 2
（带 --force 同样 rc 2；实测文件未被改动）
```

`check_baseline()` 要 `git log -1 -- <file>` 有历史，而**新一天的文件必然没有** ⇒
`daily` 在每天的第一条上**必被拒**，`--force` 也不绕。变通办法一直是「先手写标题行
单独提交一次」——**这不是没人报，是报了之后每人每天自己绕过去了**（本仓库 09-30 当天
就是这么绕的）。

**修法（按 mode 分流）**：`board`（全站唯一一份，出事即全板可见）**保持严格**；
`daily`（一天一份、当天首条本就无历史）只拒**真危险**的那一种——被 `.gitignore`
覆盖（写了也看不见），未提交的新文件放行并提示提交。

⚠️ **同一病灶有两段，只改一处会当场崩**：放行后脚本紧接着 `text = open(path).read()`
——**它同样假设文件已存在**，实测立刻 `FileNotFoundError`。两处必须一起改成
`if os.path.exists(path) else ""`。**「门禁允许的情形」必须顺着调用链一路走通，否则
只是把报错从门禁挪到了下一行。**

### ② 回执口径残留：门禁查「合并结果」，回执报「本次片段」


### ⑤ ⚠️ 跨书扫描的两条硬伤（本实例自己踩的，结论「对」但方法「错」）

2. **`out=$(cmd) && … | grep -q …` 会在 cmd 非零退出时让整条 `&&` 链短路**——

   ⇒ **命令替换后用 `;` 或显式 `|| true`**；不要把「命令是否执行」与「结果是否匹配」绑在同一根 `&&` 上。
