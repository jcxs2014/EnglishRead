# AA · 「零命中」取证机制订正（2026-10-21）

> **这是证据，不是规则。** 规则在 `docs/rules/30-writing.md` 坑字典 **7b** 与 `docs/rules/审查表.md` 的 **R5-补**。
> 本文件回答「那条判据为什么存在、当初错在哪、怎么被发现的」。

## 一、事件

《The Dues & Don'ts of Magic》第八轮复核，审查方（异实例）报出 3 条以「全书查无」为前提的缺陷，执行方回 `text/` 取证后**三条前提全部不成立**：

| 编号 | 审查方的前提 | 原文实际 | 结论 |
|---|---|---|---|
| C10-1 | 全书 `lightning/bolt/struck by` 零命中 ⇒ 「被雷劈过五次」是凭空补的 | `text/ch10:265` "It's like seeing someone get **struck by lightning five times** in a row and still be alive." | 前提错，缺陷**不成立**（真缺陷是译文丢了「像」，把比喻写成事实） |
| P25-1 | 「seven 全章零命中」⇒ 「七个红大衣士兵」无出处 | `text/ch25:137` "Behind him were **seven other** soldiers" | 前提错 |
| P11-2 | 军营谚语全章未覆盖 | `ch11 doddering around.md:13` 已有 | 前提错（只查了引语块、没查导航层） |

审查方随后认错，提交 `c79b3770b`，在 `docs/rules/审查表.md` 新增 **R5-补**：「零命中」类断言必须附命令与输出，交替匹配一律 `grep -E`。

## 二、R5-补 初版的机制归因**不成立**（本轮订正的起因）

R5-补 初版写：

> macOS 的 **BSD grep 里 `\|` 不生效**（写成 `grep 'a\|b'` 会当字面量匹配，返回空而不报错）

**本机实测反例**（`/usr/bin/grep --version` → `grep (BSD grep, GNU compatible) 2.6.0-FreeBSD`）：

```bash
$ /usr/bin/grep -c 'lightning\|bolt' text/ch10_*.txt
2                       # ← \| 是生效的，不是 0
$ /usr/bin/grep -cE 'lightning|struck by' text/ch10_*.txt
1
$ /usr/bin/grep -c 'lightning' text/ch10_*.txt
1
```

⇒ **「BSD grep 的 `\|` 失效」这条归因在本机不成立**；若照它去改规则，会得出「只要用 `-E` 就安全」的结论。

## 三、真正的机制：**ignore 感知的搜索工具跳过 gitignored 目录**

`text/` 被全局 ignore 规则排除：

```bash
$ git check-ignore -v notes/books/.../text/ch10_....txt
.gitignore:132:notes*/books/**/text/    notes/books/.../text/ch10_....txt
```

于是**同一份文件，两类工具结论相反**：

| 取证方式 | 命令 | 结果 | 退出码 |
|---|---|---|---|
| `git grep`（显式路径） | `git grep -c 'lightning' -- notes/books/.../text` | **空输出** | **1**（与「真查无」不可区分） |
| `git grep`（全库无路径） | `git grep -c 'lightning'` | 只报已追踪文件（`text/` 不在其中） | 0 |
| BSD grep 显式路径 | `/usr/bin/grep -c 'lightning' text/*.txt` | **命中 1** | 0 |
| BSD grep 递归目录 | `/usr/bin/grep -rc 'lightning' text/` | **命中 1** | 0 |

⇒ **假零命中的成因是「工具类型」，不是「模式写法」**。
⇒ **只把 `grep 'a\|b'` 改成 `grep -E 'a|b'` 防不住**：模式改对，在被跳过的目录上仍然为空。

## 四、两类连带的取证坑（同一轮实测）

1. **模式与原文用词/词形不一致 ⇒ 同样假零命中**：`text/ch25:137` 是 "Behind him were **seven other** soldiers"，
   查 "seven soldiers" 必然为空（漏词）；查 "blond" 查不到 "blonde"。
2. **纯子串会误命中**：`grep 'bolt'` 命中 `text/ch10:217` 的 "bolt **out** the front door"——与「雷击」无关。
   ⇒ 查单词加 `-w`。
3. **退出码必须单独读**：`git grep … | head -5; echo $?` 取到的是 `head` 的退出码，不是 `git grep` 的。
   本轮第一次实测就踩了这个坑（把 `head` 的 0 当成 `git grep` 的 0）。正确写法：`out=$(cmd 2>&1); rc=$?`。

## 五、订正后的落点

- `docs/rules/30-writing.md` 坑字典 **7b**（写作侧取证工具的载体）：取证三件套＝**显式路径 + 贴命令 + 读退出码**；禁用 `git grep` 与 rg 系默认 ignore 规则。
- `docs/rules/审查表.md` **R5-补**（审查侧判据的载体）：「零命中」必须贴**命令 + 输出 + 退出码**；给不出命令只能写「未核」。

## 六、通用判据（可迁移）

> **「零命中」是待复核的断言，不是证据。**
> 报它之前先证明三件事：① 命令打到了**该去的文件**（ignore 规则会不会跳过它）② 模式与原文**用词一致** ③ 退出码**是真的**。
> 三者任一未证 ⇒ 只能写「未核」，不能当阻断依据。
>
> 同族提醒：**「报 0」有两种含义——查过没查到（干净）与根本没进扫描集（没查）。** 区分靠阴性对照，不靠读源码。
