## 2. 五条「检查器会骗人」的实测（新会话最该先知道的）

1. **lane ⑭ 只核每条总览引语的头 40–52 字**（`scripts/overviewcheck/verbatim.py:373` `fpc[:52] in full or fpc[:40] in full`）。开头抄对、后半句自造，照样打 ✅。实证：`the-corpse-collectors` 概述 15/15 全绿，实际 B1 后半句是编的。
2. **lane ⑲ 的解析器是四个坑叠出来的**：`> **字段**` 前缀、全角冒号块头（`> **原句 1：**`）、引文独占一行被并进字段、标签变体（`为什么这一句这样写`）。**它不认识某种写法时会静默不查**，报「无法判定」或密度虚高——见到这两种现象先怀疑解析器，不要先改 md。
3. **lane ㉒ 必须做编号偏移兜底**：`# ㉒` 直接比章号会把「text/ 按 epub 顺序编号」误判成少写（`lost-and-found` 偏移 +3、`night-calls` 是 `ch01_1.txt` 纯数字命名）。工具已按「章题 slug → 章号+偏移」两级配对。
4. **`gate.sh` 是双轨**：退出码层（②③⑦⑧⑲⑳⑮㉒）+ 文本层 ❌。两层不一致时脚本会自报，**别只看最后那行「0 条阻断型」**。
5. **`verify_quotes` 的分段验证挡不住「同一自然段里隔了 2,487 字符的拼接」**；`structure.py order` 遇到「展平后非唯一命中」会判 `❓ 不可判定`（不是缺陷）。

## 4. 用户偏好（长期有效，比规则更不易变）

- **先量后修**：任何「我觉得有问题」都要先跑工具或 grep 出数字，再决定改不改。
- **不加规则、不改判据**，除非量出来确实有问题；改判据要写明影响面与存量数字。
- **修复只动必要处**：禁整文件 `write` 覆盖、禁跨块正则替换；批量前先改 1 条验证判据成立。
- **git**：`git add` 只加本任务路径；`git commit -- <路径>`（pathspec）；**push 必须用户明确指令**（"推送"/"push"/"已确认"）。
- **审查四档**：T0 机器（≈5 min）→ T1 快审（默认，`审查表 §0.3` 分档抽样 + 缺陷密度停手）→ T2 断言全扫（≥3 条阻断自动进）→ T3 深审（须用户确认）。
- **子代理只做 R1 素读**（每批 ≤3），R2 之后的判定不外派。
